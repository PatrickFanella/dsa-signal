# Identity and Entitlement Contract

This is the normative Task 3 v1 profile. **MUST** and **MUST NOT** are absolute. All text and JSON bytes are UTF-8. `base64url` is RFC 4648 URL-safe base64 without `=`.

## Namespaces, DID profile, and handoff

The one-time identity handoff returns only `{ did, audience, authenticatedAt, expiresIn }`. `audience` is the canonical allowlisted PWA HTTPS origin; `expiresIn` is exactly `60`; and the entitlement `sub` equals `did` byte-for-byte. Before establishing an identity session, the control plane parses `authenticatedAt` as RFC 3339 date-time with `Z` or numeric offset and captures its authoritative server `now` exactly once. It rejects `authenticatedAt > now + 30 seconds` and `now >= authenticatedAt + 60 seconds`; the PWA performs the same check only as defense in depth. Both require `audience` to exactly equal the configured PWA origin, and neither accepts a stale handoff.

A bare DID has 7--2048 UTF-8 bytes and follows the DID Core ABNF `did = "did:" method-name ":" method-specific-id`, where `method-name = 1*("a"-"z" / DIGIT)`, `method-specific-id = *( *idchar ":" ) 1*idchar`, and `idchar = ALPHA / DIGIT / "." / "-" / "_" / pct-encoded`; `pct-encoded` is `%` followed by two hexadecimal digits. The stricter configured-method profile below rejects trailing or empty segments, malformed percent encoding, URL wrappers, `/`, `?`, and `#`. No normalization, decoding, or case folding occurs: canonical authenticated DID bytes are authoritative. DID:web hostname URL parsing is rejection-only and never normalizes or returns a parsed hostname.

This v1 profile is deliberately a **subset**, not a claim to universally validate every DID Core-permitted DID. After generic parsing it accepts only configured ATProto methods, initially `plc` and `web`:

* `did:plc` is exactly `did:plc:` followed by 24 lowercase base32 characters `[a-z2-7]{24}`.
* `did:web` is exactly `did:web:` followed by an ASCII lowercase DNS hostname (non-final labels are `[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?`; the final label has that grammar and MUST contain at least one lowercase ASCII letter `[a-z]`; labels are dot-separated and the total hostname is <=253 bytes), optionally `%3A` or `%3a` followed by canonical decimal port `1`--`65535` (no leading zeroes), followed by zero or more literal-colon-separated nonempty path segments. Each segment is one or more `[A-Za-z0-9._-]` characters or valid `pct-encoded` triplets. Literal `~` is excluded by DID Core; encoded `%7E` is valid. The hostname is rejected if `node:net isIP(host)` identifies an IP or WHATWG parsing of synthetic `https://${host}` changes its `.hostname`; parsing is rejection-only and never normalization. This rejects canonical IPv4 and aliases such as `127.1`, `2130706433`, `0177.0.0.1`, `0x7f.1`, `0x7f000001`, and `127.0x1` while retaining ordinary and punycode DNS names. This represents the DID:web hostname, optional percent-encoded port, and path while keeping URL delimiters out of the DID. A generic DID Core edge outside these method rules is rejected by this v1 subset.

These values are different namespaces: handoff `audience` is the PWA origin; entitlement `aud` is literal `dsa-signal`; proof `origin` is that canonical allowlisted PWA origin; eventual OIDC `aud` is the MAS client ID. Entitlement `iss` is the authorized issuer's exact bare DID. MAS/OIDC `sub` is a separate pairwise opaque identifier, never a DID or Matrix ID.

## Compact entitlement

The credential is compact JWS/JWT with UTF-8 JSON and no unprotected header. Its protected header has exactly `alg`, `typ`, and `kid`: `{"alg":"ES256","typ":"dsa-signal-membership+jwt","kid":"<issuer DID>#<fragment>"}`. The compact credential is at most 8192 UTF-8 bytes, its decoded protected header at most 1024 bytes, its decoded payload at most 4096 bytes, and `kid` at most 2113 UTF-8 bytes. `alg` and `typ` have those exact values; `kid` is mandatory. Reject `jwk`, `jku`, `x5u`, `crit`, and every unknown key. `kid` is `${iss}#<fragment>`; the fragment is 1--64 `[A-Za-z0-9._-]` bytes. Resolve it only by exact lookup in cached issuer policy, never from a token-directed network lookup.

The payload is recursively strict and exactly `{"iss":"<bare DID>","sub":"<bare DID>","aud":"dsa-signal","iat":0,"exp":0,"jti":"<43 chars>","cnf":{"jkt":"<43 chars>"},"entitlement":"chat","policyVersion":"<version>"}`. `jti` is 32 random bytes encoded in 43 base64url characters and is unique by exact `(iss,jti)`; `cnf.jkt` is 32 bytes/43 base64url characters. `policyVersion` matches `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, is issuer-scoped, and is compared exactly.

`iat` and `exp` are finite safe integer Unix seconds. Structural parsing requires `exp > iat` and `exp - iat <= 900`. Using the one captured authoritative seconds `now`, reject `iat > now + 30`, `exp <= now`, and `exp > now + 900`; there is no expiry leeway. `authenticatedAt` validation is separate from NumericDate validation.

## Issuer policy and holder key

Only signed, versioned cached snapshots rooted in configured DIDs may authorize. The snapshot is a compact ES256 JWS capped at 16 KiB. Its protected header is exactly `{"alg":"ES256","typ":"dsa-signal-issuer-policy+jws","kid":"<configured root DID>#<fragment>"}`; the fragment is 1--64 `[A-Za-z0-9._-]` bytes and the exact `kid` selects a statically configured P-256 root public JWK. Every public JWK in this contract is recursively exact `{"kty":"EC","crv":"P-256","x":"<43 canonical base64url chars>","y":"<43 canonical base64url chars>"}` with 32-byte decoded coordinates and no `d`, `alg`, `use`, `key_ops`, or extra member. Its recursively strict payload is exactly `{"version":"v1","policyVersion":"<version>","policyUri":"<at-uri>","rootDid":"<configured root DID>","issuedAt":<Unix seconds>,"freshUntil":<Unix seconds>,"issuers":[...]}`. All timestamps are finite safe-integer Unix seconds. `policyUri` is at most 2048 UTF-8 bytes and exactly `at://<rootDid>/us.dsaslate.temp.dsaPolicy/<rkey>` where `rkey` is 1--512 `[A-Za-z0-9._~:-]` bytes. `issuers` has 1--256 entries, unique exact `did` values, and each entry is exactly `{"did":"<issuer DID>","policies":[...],"keys":[...]}`. `policies` has 1--64 unique exact entries `{"version":"<version>","state":"active|retiring|revoked","transitionedAt":<Unix seconds>}`. `keys` has 1--64 unique exact entries `{"kid":"<issuer DID>#<fragment>","state":"active|retiring|revoked","transitionedAt":<Unix seconds>,"publicJwk":<exact public JWK>}`. Arrays must already be sorted by their exact identifier bytes; normalization or duplicate identifiers reject the snapshot. `freshUntil > issuedAt`, `freshUntil <= issuedAt + POLICY_MAX_STALENESS_SECONDS`, `issuedAt <= decision_now`, and configured `POLICY_MAX_STALENESS_SECONDS` is at most 86400. This strict policy-signing clock is separate from the membership credential clock skew.

Policy ingress is an operator-only CLI, never a public HTTP route. `pnpm --filter '*api' refresh-policy -- --file <owned-path>` reads at most 16384 exact bytes from a regular non-symlink file, requires restrictive owner-only write permissions, uses a five-second abort timeout for Foundation, verifies before persistence, emits no snapshot/provenance bytes, and exits nonzero on failure. The root-operated issuer publication process is responsible for delivering this signed file. Initial bootstrap runs the same command before entitlement traffic; with no active fresh policy, challenge and verification fail closed as `503` while `/health` remains available. Refresh must run before half the configured staleness window and alerts on one failure.

Refresh verifies the root signature, strict schema, configured root and policy version, then calls `FoundationClient.resolveAuthority({uri: policyUri, depth: 16})`. Activation requires `deletedAt` to be absent and exact selected provenance `{"uri":"<policyUri>","cid":"<1--128 printable ASCII chars>","repoDid":"<rootDid>","repoRev":"<1--64 printable ASCII chars>","sequence":<nonnegative safe integer>,"observedAt":"<RFC3339>","status":"verified","authority":{"status":"official","policyUri":"<policyUri>","policyVersion":"<policyVersion>","rootDid":"<rootDid>","evaluatedAt":"<RFC3339>"}}`; all extra Foundation response fields are discarded before encryption. The source `authority.status`, root, URI, version, and selected values must agree exactly, and activation requires `decision_now < freshUntil`. The encrypted snapshot envelope stores the exact signed bytes and this selected provenance record; its catalog digest is SHA-256 of the exact compact-JWS UTF-8 bytes, without JSON canonicalization or reserialization. A refresh transaction locks the active-policy singleton, inserts the authenticated envelope/snapshot, switches the pointer, and inserts the coarse audit event atomically. Authorization takes a conflicting share lock on that pointer and rechecks the same snapshot ID and freshness before commit. It never authorizes directly from one live Foundation response. An active key accepts only an exact active policy version. A retiring key and retiring policy version are accepted only while both satisfy `decision_now < transitionedAt + 900`; revoked keys or policies reject immediately. Root JWK rotation is configuration-first and old root keys remain until no signed snapshot can be active.

The browser creates a non-extractable WebCrypto ECDSA P-256 private key. Its public JWK has exactly `kty`, `crv`, `x`, `y`: `kty:"EC"`, `crv:"P-256"`, 43-character/32-byte base64url `x` and `y`, no `d`, and no other member. RFC 7638 `jkt` is SHA-256 then base64url of exact UTF-8 JSON `{"crv":"P-256","kty":"EC","x":"...","y":"..."}`.

### Monotonic policy activation

Under the active-policy lock, an incoming root-signed `issuedAt` MUST be strictly greater than the active snapshot's `signed_at`, compared as exact timestamptz seconds. Older and equal signed policies, including still-fresh exact replays, MUST fail coarsely before envelope, snapshot, pointer, or audit writes. Bootstrap has no prior snapshot. The database independently enforces the same strict increase on active-pointer updates. Foundation provenance does not bind the compact signed bytes; only the configured root-signature verification does.

## HTTP profile v1

The external API is reverse-proxied under the PWA origin: `PUBLIC_BASE_URL.origin` equals `PWA_ORIGIN` byte-for-byte. `POST /v1/identity/sessions`, `POST /v1/entitlements/challenges`, and `POST /v1/entitlements/verifications` are non-redirecting. They require exactly one `Accept`, `Content-Type`, and `Origin` header; `Accept` is exactly `application/json`, media type matching is ASCII case-insensitive but has no parameters, and `Origin` exactly equals `PWA_ORIGIN`. `Content-Encoding` is unsupported and returns 415. Responses are JSON with `Content-Type: application/json`, `Cache-Control: no-store`, and `Referrer-Policy: no-referrer`. Challenge and verification require a valid same-origin secure identity session; identity-session bootstrap is explicitly exempt from prior-session authentication. No CORS credential sharing, cross-origin caller, proxy-derived origin, or redirect is permitted. Identity and challenge bodies are capped at 1024 raw octets and verification bodies at 16384 raw octets, inclusive, before UTF-8 decoding. Declared or streamed overflow returns 413; invalid UTF-8, duplicate singleton headers, duplicate JSON members including escaped-equivalent names, and query strings return 400. An aborted body returns 400 only if the connection remains writable; otherwise the server terminates it without an application response. Request precedence is route/method, `Accept`, media type/encoding, declared/streamed size, exact Origin (400), secure-session validation where required (401), strict JSON schema, then service decision. Other paths including `/health` keep the normal API response; these three paths with a non-POST method return normal API `405` with `Allow: POST`.

Identity-session request is exactly `{"version":"v1","code":"<43 base64url chars>","verifier":"<43--128 RFC 7636 unreserved chars>","audience":"<PWA_ORIGIN>"}`. The server, never the browser, calls `FoundationClient.exchangeIdentityHandoff` against configured TLS `FOUNDATION_BASE_URL`; a browser-supplied handoff result is never accepted. Every Foundation response body used by dsa-signal is capped at 65536 bytes before the published client parses status or JSON: a canonical nonnegative `Content-Length` over the cap, malformed or duplicate length, streamed overflow, missing/failed stream, or abort fails closed without retaining or exposing body bytes. The returned DID, audience, `expiresIn:60`, and `authenticatedAt` pass the exact handoff checks above using one PostgreSQL clock. On `201`, return exactly `{"version":"v1","result":"authenticated"}` and issue `__Host-dsa_signal_session=v1.<43-char random session ID>.<43-char HMAC tag>; Path=/; Max-Age=900; HttpOnly; Secure; SameSite=Strict` with no Domain. The tag is HMAC-SHA-256 with `COOKIE_KEY` over exact `dsa-signal-cookie:v1`, NUL, and the session-ID ASCII bytes. Persistence fingerprints only the opaque session-ID bytes, not cookie serialization. Zero or one target cookie is accepted; duplicate target-cookie names return 400 and clear with the same attributes plus `Max-Age=0`. A malformed, expired, revoked, or unknown existing cookie is cleared but does not prevent a valid bootstrap exchange. One valid existing session is revoked only in the same successful transaction that creates its replacement. No handoff code, verifier, result, plaintext DID, cookie, or session ID is logged or persisted.

Challenge request is exactly `{"version":"v1","jkt":"<jkt>"}`. On `201`, return exactly `{"version":"v1","challenge":"<43 chars>","expiresAt":<Unix seconds>}`. The server generates a random 32-byte challenge, expires it server-side in <=120 seconds, and binds it to browser session, exact DID, JKT, entitlement audience, and canonical origin.

Verification request is recursively strict and exactly `{"version":"v1","credential":"<compact JWS>","publicJwk":{"kty":"EC","crv":"P-256","x":"<43 chars>","y":"<43 chars>"},"challenge":"<43 chars>","signature":"<86 chars>","idempotencyKey":"<43 chars>"}`. Sign exact UTF-8 bytes with LF separators and no terminal LF: `dsa-signal-proof:v1\n<challenge>\n<origin>\ndsa-signal\n<did>\n<jkt>\n<credential-jti>`. Use ECDSA P-256 SHA-256; `signature` is base64url raw 64-byte `r || s`, never DER. Verify credential/policy, public-JWK/JKT, bindings, and signature.

All three endpoints use the exact error envelope `{"version":"v1","result":"rejected","error":"<code>"}`. They return `400 invalid_request` for malformed/schema/version/header/origin input, `401 rejected` for a missing/invalid secure identity session or origin binding, `406 invalid_request` for unacceptable `Accept`, `413 invalid_request` for an oversized body, `415 invalid_request` for media type, and `503 unavailable` for fail-closed Foundation, policy, clock, crypto, or storage state. A capped or malformed Foundation response is a coarse Foundation failure and returns `503 unavailable`; it creates neither an identity session nor policy persistence. Identity-session exchange maps a Foundation invalid/replayed code to `401 rejected` and dependency failure to `503 unavailable`; it never exposes Foundation errors. Verification additionally returns `200 {"version":"v1","result":"authorized"}` for a committed authorization or matching idempotent replay, `401 rejected` for every credential, signature, expiry, challenge, or replay rejection, and `409 conflict` for an idempotency key with different request bytes or session binding. No error reveals crypto, policy, replay, or binding detail. Pre-parse transport failures are not idempotency records; after strict verification-request parsing, coarse deterministic `200`, `401`, and `409` outcomes may be committed.

## Replay, idempotency, and persistence

Raw challenge, idempotency key, JTI, request bytes, credential, JWK, and signature are forbidden from persistence. Five separate dedicated 32-byte server HMAC key rings are used (not the pairwise-subject key). A fingerprint is base64url(HMAC-SHA-256(key, exact bytes)); each row stores its key ID and output. Inputs are:

* challenge: ASCII `dsa-signal-challenge-fingerprint:v1`, NUL, then decoded 32 challenge bytes;
* session binding: ASCII `dsa-signal-session-fingerprint:v1`, NUL, then UTF-8 bytes of the opaque server-side session identifier (never the cookie serialization);
* issuer-scoped JTI: ASCII `dsa-signal-jti-fingerprint:v1`, NUL, UTF-8 exact issuer DID bytes, NUL, then decoded 32 JTI bytes;
* idempotency key: ASCII `dsa-signal-idempotency-fingerprint:v1`, NUL, then decoded 32 idempotency-key bytes;
* request: ASCII `dsa-signal-request-fingerprint:v1`, NUL, ASCII media type `application/json`, NUL, ASCII profile version `v1`, NUL, then the capped raw HTTP body bytes exactly as received.

Key IDs remain available for at least the maximum applicable row TTL during rotation. A challenge row contains only its challenge and session-binding fingerprints/key IDs, encrypted DID-mapping reference (never plaintext DID), JKT, `aud`, canonical origin, and created/expiry/consumed timestamps; TTL is <=120 seconds. During the final idempotency insert, the transaction captures one PostgreSQL `clock_timestamp()` as `created_at`, sets `expires_at = created_at + interval '60 seconds'`, and commits immediately after the insert; this is the normative and implementable 60-second retry anchor. An idempotency row contains only idempotency, request, and session-binding fingerprints with their key IDs, coarse `{HTTP status, version, result/error}`, and those timestamps. This immutable fingerprint binding is not a foreign key to the shorter-lived session row. A JTI fingerprint lasts only through credential expiry plus bounded skew (at most 15 minutes +30 seconds); issuer, policy, decision, and timestamps are allowed audit metadata. No credential body or raw digest is stored.

After the capped raw-body read completes, compute the request fingerprint immediately and before ordinary JSON parsing or any logging. The read remains bounded to 16 KiB and preserves the raw bytes. It is a keyed fingerprint, not a persisted raw digest. “Identical” means identical body bytes, media type, and profile version. After validating the current secure session and origin, acquire a transaction advisory lock derived from the active idempotency fingerprint, then lookup every retained idempotency-key alias before replay rejection. A matching key/request/session-binding fingerprint returns the committed coarse result; a different request or session binding returns `409`; otherwise replay rejection is `401`. Capture one `decision_now = clock_timestamp()` after lock acquisition and use it for session, policy, claim, challenge, JTI, entitlement, and audit checks. Lock the active-policy singleton against refresh. Challenge consumption, issuer-scoped JTI uniqueness, entitlement authorization, audit, and idempotency-result commit occur in one database transaction. The final idempotency insert separately captures `idempotency_created_at = clock_timestamp()`, sets expiry exactly 60 seconds later, and is followed by immediate commit; it is not a second authorization-decision clock. Concurrent identical requests read the committed winner; different idempotency keys reusing one JTI permit exactly one authorization. Retry serialization/deadlock failures finitely, then fail closed as `503`. Database uniqueness constraints and transaction isolation provide multi-instance semantics; expiry cleanup deletes expired challenge/idempotency/JTI rows and expired-key material only after its maximum TTL. HMAC write-key rotation follows only the dedicated v1 outage-only section below.

The runtime role has no direct `DELETE` or `TRUNCATE` privilege. The retention role has no direct table privilege and may invoke only the migration-owned, expiry-guarded cleanup function. That function deletes parent replay/idempotency rows only after their retention deadlines so aliases cascade atomically; sessions only after absolute expiry plus 30 seconds; entitlements only after expiry plus 30 seconds; and coarse audit events only after 90 days. It rejects a newer audit cutoff. Migration-owner and retention credentials are never present in the API process or container.

One-time control-plane login state is 32 random bytes. Persistence stores only SHA-256 of exact bytes `dsa-signal-login-state:v1`, NUL, then the decoded state; it expires exactly five minutes after the database creation clock and is atomically consumed. It never stores the raw state or PKCE verifier. A secure identity session stores only its session-binding fingerprint, encrypted DID-mapping reference, canonical origin, and timestamps. It has a five-minute idle TTL and a 15-minute absolute TTL; a revoked session row remains only until its original absolute expiry plus 30 seconds. Session-binding HMAC key material remains available through that bound. Idle expiry advances to `LEAST(decision_now + 300 seconds, absolute_expiry)` only for committed challenge `201` and parsed verification `200`, deterministic `401`, or `409` outcomes, including a bound idempotent replay. Pre-schema failures, identity-bootstrap failures, and `503` outcomes never renew a session.

Plaintext DIDs and signed issuer-policy snapshots are application-encrypted before persistence with a versioned AES-256-GCM key ring. Each envelope stores the key ID, a fresh 12-byte nonce, and ciphertext including the 16-byte tag. DID-mapping AAD is exact UTF-8 `dsa-signal-did-mapping:v1\0<mapping UUID>\0<sector>`; issuer-policy AAD is exact UTF-8 `dsa-signal-policy-snapshot:v1\0<snapshot UUID>\0<policy version>`. Signed policy bytes and provenance form one encrypted envelope; plaintext issuer DIDs, `kid` values, and free-form policy JSON are forbidden columns. Encryption keys remain available until every referenced mapping, policy snapshot, and corresponding envelope row is actually erased; logical expiry alone never permits key deletion while retained audit/FK rows preserve the snapshot. The active entitlement table is exactly `control_plane.entitlements`; Task 6 migration 0004 adds its OIDC epoch, session binding, and generation while preserving and validating the existing exact `policy_snapshot_id` foreign key.

## HMAC write-key rotation (v1)

The implementation writes only active aliases. v1 permits only outage/quiescence activation: stop all writers and instances, block traffic, drain at least 930 seconds (maximum JTI retention) and 60 seconds (idempotency retention), preflight retained keys, deploy every instance with one new active epoch, then restart. Rolling mixed active epochs, online activation, and dual-write are prohibited. Retain old keys until all references expire. Rollback is allowed only while traffic is blocked and all instances use a single previously validated configuration; do not roll back after new-epoch rows are written.

## Pairwise subject and handling

`sector` is immutable configured data, never request-derived. In v1 it is deliberately narrower than a WHATWG URL: an ASCII lowercase DNS-hostname HTTPS origin only (non-final labels are `[a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?`; the final label has that grammar and MUST contain at least one lowercase ASCII letter `[a-z]`; no trailing dot), optionally with a canonical decimal port `1`--`65535` (no leading zeroes); port `0`, explicit `443`, IPv4 and IPv6 special host syntax, and every path/query/fragment/userinfo form are rejected. The hostname is rejected if `node:net isIP(host)` identifies an IP or WHATWG parsing of synthetic `https://${host}` changes its `.hostname`; parsing is rejection-only and never normalization. This rejects canonical IPv4 and aliases such as `127.1`, `2130706433`, `0177.0.0.1`, `0x7f.1`, `0x7f000001`, and `127.0x1` while retaining ordinary and punycode DNS names. It is <=255 bytes. DID contains no NUL and is <=2048 UTF-8 bytes. The dedicated subject HMAC key ring has versioned exact 32-byte keys. Subject is 43-character base64url HMAC-SHA-256 of exact UTF-8 `dsa-signal-subject:v1\0${sector}\0${did}`. Encrypted DID+sector-to-subject mappings are authoritative across rotation; every key ID referenced by a mapping remains available for that mapping's lifetime, and lookup tests every retained subject-key version rather than silently deriving a new identity. For Task 6, `OIDC_SECTOR` is this exact MAS HTTPS DNS origin and the provider MUST return the stored authoritative `did_mappings.subject` as pairwise `sub`; it MUST NOT decrypt the DID or derive a subject during an OIDC request.

Sensitive transient data never enters logs, APM, traces, errors, crash reports, support, or backups: encoded JWTs, decoded claim bodies, proofs, raw challenges/JTIs/idempotency keys, signatures, raw request bytes, and plaintext DIDs. Encrypted DID mappings and the explicitly permitted keyed fingerprints, JKT, audience/origin, issuer/policy metadata, coarse decisions, and timestamps may appear only in encrypted database backups under the privacy contract. The membership issuer never receives the control-plane proof challenge; it sees issuance inputs and JTI only. A new holder key needs a fresh handoff and entitlement. Entitlement expiry/revocation denies future Matrix/MAS authorization but cannot retract downloaded plaintext or keys.
